## Context

The implementor command currently lives inside
`home-modules/project-manager/automated-development-workflows/implementor` as a
`pkgs.writeShellApplication`. Its script contains the complete workflow,
including OpenSpec discovery, agent selection, temporary worktrees, provider
queries, publication, and cleanup. The module provides package override
options so consumers can supply Git, jq, OpenSpec, `opencode-agent`, `gh`, and
`tea` packages.

The flake currently assembles packages from `default.nix`. `opencode-agent` is
already exposed as a package, but its direct runner expects an `opencode`
executable at runtime and uses generated agent environments packaged with the
runner. A direct implementor package must provide the same runtime closure and
must not rely on files generated by Home Manager.

## Goals / Non-Goals

**Goals:**

- Support `nix run .#openspec-implementor -- <existing arguments>`.
- Support remote-flake usage such as
  `nix run github:john-craig/nixpkgs-apocrypha#openspec-implementor -- ...`.
- Reuse one command implementation for Home Manager and flake execution.
- Include a runnable OpenCode executable and the packaged agent environments in
  the direct package closure.
- Preserve explicit Home Manager package overrides and configured defaults.
- Test package evaluation, help output, argument validation, and a fake remote
  workflow without live provider credentials.

**Non-Goals:**

- Do not change the implementor CLI, branch naming, provider semantics, or
  agent prompt beyond what is required for packaging.
- Do not deploy Home Manager or write user configuration during `nix run`.
- Do not embed GitHub/Gitea credentials, OpenCode provider credentials, or
  machine-specific authentication files in the package.
- Do not add a second source of agent definitions or workflow logic.
- Do not make `nix run` a dry-run mode; it retains the existing publishing
  behavior.

## Decisions

### Shared runner construction

Move the command construction into a reusable package function or package
definition under `pkgs/openspec-implementor`. The function should accept the
runtime packages and the existing workflow defaults, then return the same
`openspec-implementor` executable.

The Home Manager module should use this shared construction while passing its
configured package overrides and options. The flake package should use the
repository's package set and expose the same defaults. The two paths must not
duplicate the shell implementation.

### Flake package closure

The direct package should provide these commands through its runtime inputs:

- Git;
- jq;
- OpenSpec;
- the flake-provided `opencode-agent` package;
- the OpenCode executable required by `opencode-agent`;
- `gh` for GitHub publication;
- `tea` for Gitea publication.

The package may include both provider CLIs so runtime provider selection remains
unchanged. Credentials, host configuration, SSH keys, and provider state stay
outside the Nix store and are discovered through the normal CLI mechanisms.

### OpenCode package and agent environments

The flake package construction should use the existing `opencode-nix` overlay
when necessary to resolve `pkgs.opencode`. It should pass the repository's
`opencode-agent` package into the implementor runner rather than requiring a
Home Manager-installed command. `opencode-agent` remains responsible for
selecting its packaged environment and invoking `opencode run`.

The package must not set `OPENCODE_CONFIG` globally or copy user configuration.
The selected agent environment continues to come from the flake package's
generated data, while provider credentials remain runtime concerns.

### Public outputs

Expose the derivation through:

```text
default.nix: openspec-implementor
flake legacyPackages.<system>.openspec-implementor
flake packages.<system>.openspec-implementor
```

Set `meta.mainProgram = "openspec-implementor"` so `nix run` resolves the
executable predictably. The output should support:

```console
nix run .#openspec-implementor -- --help
nix run .#openspec-implementor -- --upstream URL --change NAME
```

### Home Manager compatibility

The module's public option namespace and command behavior remain stable. A
consumer that overrides `openspecPackage`, `opencodeAgentPackage`, provider
packages, `baseBranch`, `workRoot`, or `keepWorktree` must still receive those
values in the Home Manager-installed command. Package defaults may point to the
shared package implementation, but module evaluation must continue to fail
with actionable assertions when required dependencies are unavailable.

### Verification strategy

Add a focused package check that uses fake OpenSpec, agent, GitHub, and Gitea
commands plus a local bare Git repository. Verify that direct package
invocation selects the configured agent, creates and publishes the expected
branch, and cleans up temporary state. Keep the existing Home Manager module
check and assert representative behavior is equivalent.

Add a flake check for `--help`, invalid input rejection, package executable
presence, and generated package contents without credentials or machine-local
paths.

## Risks / Trade-offs

- [The Home Manager and flake runners drift] -> Construct both from one shared
  package function and test both entry points against the same fake workflow.
- [The direct closure becomes large] -> Reuse the existing packaged
  `opencode-agent` environments and accept provider CLI closure size in return
  for a self-contained `nix run` command.
- [OpenCode is unavailable in plain nixpkgs] -> Apply the existing
  `opencode-nix` overlay during flake package construction and fail evaluation
  with an explicit package error if it cannot be resolved.
- [A package accidentally captures credentials] -> Inspect the package and
  generated environments for tokens, secret contents, and machine-specific
  paths; keep authentication as runtime CLI configuration.
- [Users expect `nix run` to be non-publishing] -> Document that direct flake
  execution has the same publishing behavior as the Home Manager command and
  does not provide an implicit dry-run.

## Migration Plan

1. Extract the runner construction and add the flake package.
2. Refactor the Home Manager module to consume the shared implementation while
   preserving its options.
3. Add package exports, metadata, and focused direct-run checks.
4. Document `nix run` examples and runtime authentication requirements.
5. Run OpenSpec validation, focused checks, and the complete flake check suite.
6. Roll back by removing the package export; the existing module behavior must
   remain available throughout the change.
